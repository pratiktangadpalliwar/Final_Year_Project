## 0. Context and motivation

The previous iteration of this project (`v1` → `Final Year Project v1` → security/upgrade commits) implemented a 7-bank federated learning system on Kubernetes with:

- A FastAPI/Flask aggregation server (FedAvg + Trimmed-Mean + Krum, server-side DP, RoundManager with rollback)
- 7 client pods, one per simulated bank, each running a `watcher.py` that polled `/data/input/` for CSV drops, then trained and uploaded weights to S3
- DynamoDB for round state, S3 for model artifacts, manual `kubectl cp` for staging datasets

The system was functionally correct in code, but the dataset-staging path was the operational point of failure: bank operators had to `kubectl cp` ~500MB CSVs into per-pod ReadWriteOnce PVCs, multiple times, with no recovery on pod restart. AccessDenied on S3 (caused by drift between the configured bucket name and the IAM-allowed bucket) compounded the problem. As a result, training rounds either never started or never produced an aggregated model.

This spec rebuilds the system from scratch with three explicit goals:

1. **Make dataset distribution unbreakable.** Eliminate `kubectl cp`, eliminate per-bank PVCs, eliminate the watcher.
2. **Add a single dashboard** that lets one operator (sitting at one laptop) observe all 7 banks training in real time, control rounds, swap datasets, and inject faults.
3. **Run the demo entirely on AWS** using a single `./deploy.sh` script.

The system is intended for a final-year project demonstration in front of evaluators. Every architectural choice in this document is justified in viva-defendable terms (a "Why this matters" rationale), so that the author can explain and defend the design without it appearing autogenerated.

## 1. Decisions register

The following decisions were made during brainstorming and are locked unless this spec is revised. Each row links a question to its accepted answer.

| # | Question | Decision |
|---|---|---|
| Q1 | How should each bank pod receive its CSV dataset? | **S3 + init container.** Datasets live in `s3://<bucket>/datasets/{bank_id}.csv`. An init container downloads to an emptyDir volume before the main container starts. No PVC, no `kubectl cp`. |
| Q2 | What should the operator dashboard let me do? | **All four:** live training view, trigger/pause training, upload/swap datasets per bank, inject fault scenarios. |
| Q3 | Cluster size? | **7 banks, 3× t3.large EKS nodes.** |
| Q4 | Dashboard hosting + access? | **ALB ingress with single ADMIN_PASSWORD → JWT cookie.** |
| Q5 | Deploy mechanism? | **Single `./deploy.sh` bash script** with `--apps-only` and `--datasets-only` modes; matching `./teardown.sh`. |
| Q6 | Round trigger + service-mesh auth? | **Auto-loop rounds on server, no client↔server auth (network-isolated via ClusterIP + NetworkPolicy).** Dashboard has Pause/Resume/Reset. |
| Architecture | Dashboard wiring? | **Approach A:** monolithic fl-server (FastAPI + Uvicorn + WebSocket + React static bundle). Single image, single ALB. |
| Dashboard scope | Local-vs-global metrics? | **Both.** Top strip = 5 global metric sparklines + DP-ε counter. Each BankCard = local sparkline + 9-cell numeric grid. Drill-in modal = 16-field metric block per round, LOCAL vs GLOBAL overlay. |

## 2. System architecture

### 2.1 Topology

Single AWS region (default `us-east-1`). One EKS cluster (`fl-demo`) with one namespace (`fl`). One fl-server pod (no HA in demo). Seven fl-client pods, one per bank. One Application Load Balancer fronting the fl-server pod over HTTPS. One S3 bucket for all stateful data. No DynamoDB, no RDS, no EFS, no SQS.

```
laptop (operator)
       │ HTTPS (admin password gate → JWT cookie)
       ▼
   AWS ALB ── path /* ──► fl-server (1 pod)
                            │ ClusterIP, in-cluster
                            ▼
                      ┌────────────────────────────┐
                      │ EKS namespace "fl"          │
                      │ ┌─ fl-server pod ─────────┐ │
                      │ │ FastAPI + Uvicorn       │ │
                      │ │ React static bundle     │ │
                      │ │ WebSocket /ws/live      │ │
                      │ │ asyncio round_loop      │ │
                      │ └─────────────────────────┘ │
                      │   ▲       ▲       ▲         │
                      │   │ poll  │ poll  │ poll    │
                      │ ┌─┴──┐ ┌──┴─┐ ... ┌─┴─┐     │
                      │ │bk01│ │bk02│     │bk07│    │
                      │ └────┘ └────┘     └────┘    │
                      └─────────────────────────────┘
                                │ IRSA (no static keys)
                                ▼
              s3://fl-demo-{accountId}-{region}/
                  datasets/{bank_id}.csv      (operator-uploaded)
                  models/global_round_XXXX.pt (server-written)
                  updates/{bank_id}/round_XXXX.pt (client-written)
                  checkpoints/round_XXXX.json (RoundManager state)
                  control/state.json          (ControlPlane snapshot)
                  validation/val_set.pkl      (held-out set for global eval)
```

### 2.2 Why this shape

- **Single ALB, single image** → smallest attack surface, one DNS to remember during demo.
- **EKS over ECS/EC2** → standard FL/research deployments use Kubernetes; topology spread + pod anti-affinity prove the "distributed across institutions" story.
- **S3 as the only stateful service** → fewer moving parts to justify; RoundManager state is checkpointed to S3 every round so a server restart can resume.
- **IRSA (IAM Roles for Service Accounts)** → no static AWS keys in the cluster.
- **Long-poll over HTTP, not gRPC or message queue** → keeps the trace easy to draw on a whiteboard.
- **Auto-loop server, dashboard observes** → matches FedAvg pseudocode in McMahan et al. 2017 (defensible literature reference).

### 3.1 Why this layout

- **Three top-level modules `server/ client/ dashboard/`** mirror the three actors in any FL paper.
- **`infra/` separated from app code** → infra and app change independently.
- **One server image bundles dashboard** → fewer deploys, no CORS to explain.
- **Client and server share a hand-copied `model.py`** rather than a shared PyPI package; CI runs a hash check (`sha256sum server/app/model.py client/app/model.py` must match).
- **`round_loop.py` is its own file** → when an examiner asks "where does FedAvg actually trigger?", you open one short file.

## 4. Dataset distribution (the part that broke last time)

### 4.1 Failure modes from v1 and how they are eliminated

| Past failure | Root cause | This design |
|---|---|---|
| `kubectl cp` of 500MB CSV into pod `/data/input/` PVC | RWO PVC is single-AZ; `cp` times out on slow links; pod restart loses transient state; 7 manual operations | One-time `aws s3 cp` from operator laptop to S3, pod fetches at boot |
| Watcher polled `/data/input/` for a CSV that never arrived | Manual upload was unreliable | Watcher removed entirely; client asserts dataset exists at boot or fails fast |
| AccessDenied on S3 weight upload | IAM not bound to ServiceAccount; bucket name drift between configmap and terraform | IRSA bound at deploy time; bucket name is single source of truth (`infra/outputs.tf` → helm value → env var) |
| Three PVCs per bank × 7 banks = 21 volumes to manage | Watcher needed INPUT_DIR / DONE_DIR / ERROR_DIR | Zero PVCs; emptyDir only |

### 4.2 Mechanism — boot-time S3 download

```
deploy.sh                           one-time, on operator laptop
  └─ aws s3 cp dataset/bank_NN_*.csv s3://fl-demo-.../datasets/bank_NN_*.csv  (×7)

bank pod startup                    every cold start
  ├─ initContainer "fetch-dataset"
  │     image: amazon/aws-cli:2
  │     command: aws s3 cp s3://$BUCKET/datasets/$BANK_ID.csv /work/data/bank.csv
  │     volumeMount: /work/data  (emptyDir, sizeLimit 2Gi)
  │     IRSA: fl-client-sa → s3:GetObject on datasets/*
  │     fails fast on AccessDenied → pod stays in Init:Error → dashboard shows red BankCard
  │
  └─ main container "fl-client"
        env: DATASET_PATH=/work/data/bank.csv
        startup assertion: DATASET_PATH exists, size > 1MB
        no watcher, no INPUT/DONE/ERROR dirs
        round_runner loop drives training
```

### 4.3 Dataset swap from dashboard

```
Operator drops bank_04.csv onto BankCard
  → POST /admin/dataset/{bank_id}  (multipart, max 600MB)
  → fl-server streams body via boto3 multipart upload → s3://.../datasets/{bank_id}.csv
  → fl-server bumps ControlPlane.banks[bank_id].dataset_version += 1
  → fl-server broadcasts ws event { type: "dataset_swapped", bank_id, version }
  → client round_runner sees version mismatch on next /control poll
     → re-runs S3 download (same path) → reload preprocessor
     → continues at next round with new data
     → no pod restart needed
```

### 4.4 Why this is defensible at viva

1. RWO PVCs cannot move across AZs; emptyDir is node-local SSD, faster than EBS, and the dataset is read-only after load.
2. Real FL banks never share datasets via image registries; S3 + IRSA mirrors the production pattern of "data stays in your account, server only sees gradients".
3. Atomic S3 writes (multipart finalises only on success); client re-reads only between rounds, never mid-epoch.
4. Init container failure surfaces immediately as `Init:Error` → dashboard red card → operator has full visibility.

## 5. FL round lifecycle and control plane

### 5.1 Server-driven auto-loop

```python
# server/app/round_loop.py — pseudocode
while True:
    if control.paused:        await sleep(1); continue
    if no global model yet:   init_random_weights() → save round 0 to S3
    round = control.current_round + 1
    control.set("collecting", round)             # ws push: round_started
    await collect_updates(round, deadline=ROUND_TIMEOUT)
        # quorum: len(updates) >= max(MIN_NODES, active * QUORUM_PCT)
    if len(updates) < MIN_NODES:
        control.flag_round_stalled(round)        # ws push: round_stalled
        continue
    valid, suspicious = validator.score(updates)  # cosine + norm bound
    aggregated = aggregator.aggregate(valid, suspicious_pct)  # FedAvg / TM / Krum
    new_global = dp_engine.privatize(aggregated)
    if abs(metric_delta) > ROLLBACK_THRESHOLD and round > 5:
        round_manager.rollback()                 # restore checkpoint
        ws push: round_rolled_back
        continue
    storage.put_global(round, new_global)        # s3 models/global_round_XXXX.pt
    round_manager.checkpoint(round)              # s3 checkpoints/round_XXXX.json
    control.set("idle", round)                   # ws push: round_completed + metrics
    await sleep(INTER_ROUND_DELAY)               # default 2s
```

### 5.2 Client round runner

```python
# client/app/round_runner.py — pseudocode
last_round_trained = -1
while True:
    ctrl = GET /control/{bank_id}      # {paused, dataset_version, fault, current_round, weights_key}
    if ctrl.dataset_version > local_version: download_dataset()
    if ctrl.fault == "crash" and not crashed: sys.exit(1)
    if ctrl.fault == "straggle":              sleep(STRAGGLE_DELAY)
    if ctrl.paused or ctrl.current_round == last_round_trained:
        sleep(2); continue
    weights = storage.get(ctrl.weights_key)   # presigned URL
    new_w, metrics = trainer.train(weights, dataset, fault=ctrl.fault)
    key = f"updates/{bank_id}/round_{ctrl.current_round:04d}.pt"
    storage.put(key, new_w)
    POST /model/update {bank_id, round, weights_key:key, n_samples, metrics}
    last_round_trained = ctrl.current_round
```

### 5.3 ControlPlane data model

```python
# server/app/control_plane.py
@dataclass
class BankControl:
    dataset_version: int = 1
    fault: Literal["none","crash","straggle","byzantine","partition"] = "none"

@dataclass
class GlobalControl:
    paused: bool = False
    current_round: int = 0
    state: Literal["idle","collecting","aggregating","stalled"] = "idle"
    inter_round_delay_s: int = 2

class ControlPlane:
    banks: dict[str, BankControl]
    global_: GlobalControl
    # methods: pause(), resume(), reset_rounds(), set_fault(bank,kind),
    #          bump_dataset_version(bank), snapshot_to_s3(), restore_from_s3()
```

### 5.4 Fault injection table

| Dashboard button | ControlPlane change | Client behavior | What this proves |
|---|---|---|---|
| Crash bank_X | `fault=crash` | `sys.exit(1)` once → pod restart | Quorum tolerates missing node |
| Make bank_X straggler | `fault=straggle` | sleeps 60s before training | ROUND_TIMEOUT + partial-quorum aggregation |
| Make bank_X byzantine | `fault=byzantine` | trainer flips sign of 30% of weights | Validator + Krum suppress contribution; trust score drops |
| Partition bank_X | `fault=partition` | client `/control` poll loop sleeps until cleared | dropout-rejoin behavior; stale model detected |
| Pause | `global_.paused=true` | server skips ticks; client idles | Clean stop mid-explanation |
| Reset rounds | `current_round=0`, re-init random weights | clients see round wrap → start fresh | Fresh demo without redeploy |

### 5.5 Persistence — what survives an fl-server restart

- `s3://.../models/global_round_XXXX.pt` — every accepted global model
- `s3://.../checkpoints/round_XXXX.json` — RoundManager state (round#, trust scores, registered banks, cumulative DP-ε per bank + global)
- `s3://.../control/state.json` — ControlPlane snapshot (paused/fault/dataset_version)

On boot: fl-server reads latest checkpoint + control state → resumes auto-loop where it left off. If checkpoint read fails after 3 retries, the server refuses to start (better than serving stale state silently).

**DP-ε accounting model (clarification):** each round the client adds Gaussian noise calibrated to a per-round ε (default 5.0 from v1) and the server adds a separate Gaussian on the aggregate. The dashboard tracks the running sum of per-round ε per bank and globally. There is no hard cap enforced in code — the figure is shown for transparency and viva narrative ("after 50 rounds, bank_04 has spent ε≈250 of its theoretical privacy budget"). Changing this to a hard cap is a one-line check in `dp_engine.py` and is called out as a Phase 2 item in the implementation plan, not here.

**Round timeout (default):** `ROUND_TIMEOUT_S = 300` (carried over from v1). Straggler fault sleeps 60s, well under the timeout. Adjustable via env var on the server pod.

## 6. Dashboard — UI and API

### 6.1 Layout (single page)

- **Top bar:** brand, round#, state, banks online, cumulative DP-ε, controls (Pause / Resume / Reset / Logout).
- **Global metric strip:** five sparklines (AUC-ROC, F1, Precision, Recall, Val-loss), each labelled with current value.
- **Bank grid (4×2):** seven BankCards. Each card shows status pill (color-coded border), local val-AUC sparkline, 9-cell numeric grid (loss, auc, f1, precision, recall, accuracy, ‖w‖, σ, train-time), trust score, dataset version, n_samples, fault button, swap-CSV button.
- **Drill-in modal** (open on card click): full LOCAL vs GLOBAL overlay chart + 16-field metric block per round (val_loss, train_loss, auc, f1, precision, recall, accuracy, ‖w‖, cos→median, DP-σ, DP-ε used, n_samples, epochs, train_time, verdict, weights_key) + history scrubber.
- **Event log:** live WebSocket feed at the bottom; structured events with severity colors (info/warn/error).

### 6.2 What is tracked

**Per round, per bank (LOCAL):**

- Quality: train_loss, val_loss, val_auc, val_f1, val_precision, val_recall, val_accuracy
- Weights: ‖w‖ (L2 norm), cosine similarity to median (cheap Byzantine signal)
- Privacy: DP σ used this round, cumulative DP-ε spent by this bank
- Workload: n_samples, epochs, train time, upload time, weights_key
- Trust: trust_score (server-assigned), flagged?, rejected_by_aggregator?

**Per round (GLOBAL — server):**

- Quality: AUC, F1, precision, recall, accuracy, val_loss (against held-out validation set in S3)
- FL stats: participating banks, suspicious count, aggregation method (FedAvg/TM/Krum), rollback?
- Privacy: DP σ added by server, cumulative DP-ε of global model
- Timing: round duration, slowest bank, aggregation time

All of these are already produced by `trainer.py` + `aggregator.py` in v1. No new ML code; only new endpoints + UI.

## 7. Deployment — `deploy.sh` and `teardown.sh`

### 7.1 `deploy.sh`

A single bash script with three modes. Idempotent. Re-runnable. Prints the dashboard URL + admin password at the end.

Modes:

- `./deploy.sh` — full: terraform → docker build/push → dataset upload → val-set build → helm install → wait for ALB
- `./deploy.sh --apps-only` — skip terraform; rebuild images + helm upgrade
- `./deploy.sh --datasets-only` — only re-upload CSVs to S3

Steps in order:

1. Terraform `apply` — VPC, EKS, S3 bucket (named `${project}-${accountId}-${region}`), ECR repos, IRSA roles, ALB controller IAM, OIDC provider.
2. ECR `docker buildx build --push` — dashboard built first (output goes into `server/app/static/`), then server image, then client image. Tagged `:${git-sha}` and `:latest`.
3. `aws s3 cp` × 7 — dataset CSVs to `s3://<bucket>/datasets/{bank_id}.csv`.
4. `python3 dataset/build_val_set.py` — builds held-out validation pickle (5% stratified sample across all 7 banks); uploaded to `s3://<bucket>/validation/val_set.pkl`.
5. `helm upgrade --install fl-demo k8s/fl-chart` — passes `global.s3Bucket`, `global.imageTag`, `global.ecrBase`, `global.region`, `global.accountId`, `admin.password` (generated with `openssl rand -hex 12` if not pre-set via `FL_ADMIN_PASSWORD` env var).
6. Poll `kubectl get ingress fl-server` for ALB DNS, then print summary block:

```
==============================================================
  fl-demo deployed.
  Dashboard:  https://<alb-dns>/
  Admin pwd:  <generated-or-env>
  S3 bucket:  s3://<bucket>
  EKS:        <kubectl-context>
==============================================================
```

### 7.2 `teardown.sh`

`helm uninstall` → `kubectl delete ns fl` → `aws s3 rm <bucket> --recursive` → `terraform destroy`. Safe order ensures Helm releases are gone before terraform tries to delete the cluster.

### 7.3 Cold-deploy timeline

| Step | Approx |
|---|---|
| Terraform (VPC + EKS + S3 + ECR + IAM) | 12–15 min |
| Docker build + push (server + client) | 3–5 min |
| Dataset upload (3.5GB to same-region S3) | 1–2 min |
| Validation set build + upload | 30s |
| Helm install + ALB provisioning | 3–4 min |
| **Total cold** | **~20–25 min** |

Re-run with `--apps-only`: ~5 min (image rebuild + rolling restart).

## 8. Error handling

### 8.1 Principles

1. Fail fast at boundaries; retry only on transient I/O.
2. Boundaries = HTTP, S3, disk, env-var parsing. Internal code trusts itself.
3. Three retry classes only:
   - **transient** (network, S3 5xx, throttle, timeout) → exponential backoff, 3 tries
   - **permanent** (validation, AccessDenied, schema mismatch) → no retry, surface to dashboard
   - **expected** (paused, no work yet, dataset not ready) → silent sleep + recheck
4. All errors emit a structured event to `ws_hub` → operator sees them in the dashboard event log.

### 8.2 Per-component matrix

| Where | Error | Class | Action |
|---|---|---|---|
| Client init container | S3 download fails | transient | aws-cli built-in retry; if 3× fail, pod stuck Init:Error → red BankCard |
| Client init container | AccessDenied | permanent | crash; visible in `kubectl describe pod` + dashboard |
| Client `round_runner` | server 5xx on /control poll | transient | 3 tries with backoff; then sleep 30s and retry |
| Client `round_runner` | server 4xx (bank not registered) | permanent | re-register once, then escalate |
| Client `trainer` | unexpected exception | permanent | crash, k8s restarts pod, init container re-fetches dataset |
| Client `storage.put` weights | 5xx / throttle | transient | 3 tries; then skip this round (server's quorum still works) |
| Server `round_loop` | aggregator raises (numeric NaN) | permanent | mark round stalled, ws push, sleep, try next round |
| Server `/model/update` | invalid weights tensor (wrong shape) | permanent | 422 + ws push `{level: warn, ...}` |
| Server boot | S3 list_objects 5xx during checkpoint restore | transient | 3 tries; if all fail, refuse to start |
| Server `/admin/dataset` upload | over 600MB | permanent | 413 |
| Server `/admin/dataset` upload | S3 multipart failure mid-upload | transient | abort multipart, return 502, operator retries from dashboard |

### 8.3 Logging

Stdlib `logging` with JSON formatter → CloudWatch via fluent-bit DaemonSet (installed by terraform as part of EKS addon `aws-cloudwatch-observability`). One `correlation_id` per round propagated from server `round_loop` into client `round_runner` via `/control` payload → grep across pods works.

| ALB | 1 listener | $0.55 | |

| **Per 24h running** | | **~$9.30** | |

Cost-control mechanisms baked in:

- `teardown.sh` removes everything in <15 min — run after each work session.
- `--apps-only` mode skips terraform.
- `replicaCount: 1` for fl-server.
- Spot is a 1-line var change in `infra/variables.tf` (`capacity_type = "SPOT"`).
- CloudWatch retention = 7 days.

### 10.2 Security posture

| Layer | What we do | What we don't do | Honest framing |
|---|---|---|---|
| Network ingress | Single ALB, HTTPS only (ACM cert) | No WAF, no rate-limit | "Demo is unlisted URL + password; productionising adds WAF" |
| Authn | Single shared `ADMIN_PASSWORD` → bcrypt → JWT cookie (HttpOnly, Secure, SameSite=Strict) | No SSO | "Single operator demo; multi-tenant adds Cognito" |
| Authz | `/admin/*` and `/ws/live` require cookie; `/health`, `/static/*` open | No fine-grained roles | "One operator role; read-only role is one decorator" |
| Service-to-service | Client→Server uses ClusterIP `http://fl-server.fl.svc:8080` only | No mTLS, no HMAC | "Network-isolated; HMAC documented as Phase 2" |
| AWS auth | IRSA only — zero static AWS keys | — | Standard best practice |
| Least privilege | fl-client-sa: `s3:GetObject` on `datasets/*` + `models/*`; `s3:PutObject` on `updates/*`. fl-server-sa: full bucket | — | Explicit IAM in `infra/iam.tf` |
| Secrets at rest | Admin password → K8s Secret (etcd KMS-encrypted by default on EKS) | No external secret manager | "Could swap for AWS Secrets Manager + ESO; one chart change" |
| Image supply chain | Built from-source by deploy.sh, pushed to private ECR, tagged with git SHA, pulled by digest-pin in helm | No cosign signature verification | Honest gap — call out as future work |
| Data privacy (the FL story) | DP at client (gradient clip + Gaussian noise) + DP at server (Gaussian on aggregate). ε budget tracked per-bank and globally. | — | THIS IS THE PROJECT'S CONTRIBUTION — front-load on viva |
| NetworkPolicies | Clients can only egress to fl-server svc + S3 endpoint via VPC endpoint; server can only egress to S3 endpoint | — | "Defence in depth — even if a client image is compromised, blast radius is its own bank" |
| Audit log | Every `/admin/*` action and round transition logged structured-JSON to CloudWatch with action, target, timestamp | — | "`aws logs tail /fl-demo/server`" |

### 10.3 Out of scope (and why)

- Multi-region / multi-AZ HA — single AZ for demo; explicit cost trade-off.
- GPU training — model is ~4K params; CPU is ~10s/epoch on 500K rows. GPU = unjustified cost.
- Real OIDC/SSO on dashboard — adds Cognito complexity for a one-operator demo.
- HMAC client auth — designed in but turned off (Q6); "no auth, network-isolated" is the demo posture and is documented as such.
- PVCs / EFS — eliminated in favour of S3 + emptyDir; this is the entire fix for the prior breakage.
- DynamoDB — eliminated; round state goes to S3 JSON checkpoint.

## 11. Acceptance criteria

This rebuild is considered done when **all** of the following are true on a fresh AWS account:

1. Running `./deploy.sh` end-to-end on a fresh checkout completes successfully and prints a dashboard URL + admin password.
2. Opening the URL, logging in with the printed password, shows the dashboard with all 7 banks visible.
3. Within 5 minutes of dashboard open, at least 3 federated rounds have completed and the global AUC sparkline shows an upward trend.
4. Clicking any BankCard opens a drill-in modal showing all 16 LOCAL metric fields for that bank's last round.
5. Clicking "Make bank_04 byzantine" produces a visible event-log entry stating that the update was flagged, and bank_04's trust score on its card visibly drops.
6. Drag-dropping a CSV onto a BankCard succeeds, the dataset_version on that card increments, and within 1 round that bank's local metrics shift.
7. Clicking Pause halts round progression; clicking Resume continues from the same round.
8. `./teardown.sh` removes all AWS resources (verified by `aws s3 ls` showing the bucket gone and `aws eks list-clusters` showing the cluster gone).
9. `pytest tests/unit tests/integration` passes locally with no AWS credentials configured.
10. `tests/e2e/compose.yml` produces a green smoke test run in CI.

## 12. Risks and explicit non-goals

**Risks:**

- **EKS first-time deploy can fail on IAM eventual consistency** — Terraform may need a second `apply` if IRSA OIDC binding races. Mitigation: `deploy.sh` retries terraform once on failure with a 30s sleep.
- **ALB DNS propagation** — can take 3–5 minutes after Helm install completes. Mitigation: deploy.sh polls and prints "pending" rather than failing.
- **Image build platform** — operator laptop is Windows; uses `docker buildx --platform linux/amd64` to ensure the image is correct for EKS nodes.
- **3.5GB dataset upload over hotel wifi** — large; mitigation: `--datasets-only` mode is separable; can be run from a Cloud Shell if local upload is slow.

**Non-goals (explicit):**

- Production-grade multi-tenancy.
- Compliance-grade audit (HIPAA, GDPR data subject rights).
- Continuous re-training schedule beyond the manual demo run.
- Federated personalisation per bank (only one global model).
- Cross-cloud deployment.
